# Защита основной ветки: карточка 1.7

Дата: 2026-10-29. Статус: утверждён пользователем; выполнение разрешено.

## Цель

Выполнить условия карточки [#7](https://github.com/devops-praktik-2026/khramtsov-nasibulin/issues/7): запретить прямую запись в main, слияние без одобрения второго участника и слияние с упавшими проверками. Подтвердить запреты реальными попытками и сохранить сообщения GitHub в описании PR.

## Подходы

1. Дополнить существующий ruleset: настройки защиты main собраны в одном месте, сохраняются действующие ограничения.
2. Создать дополнительный ruleset: существующий не меняется, но итоговая защита распределяется между двумя правилами.

Пользователь выбрал первый подход. Это небольшое изменение настроек с практической проверкой.

## Настройки

Обновить ruleset `23659601` (`Disable force push in main`) в репозитории `devops-praktik-2026/khramtsov-nasibulin`:

- Переименовать в `Защита main`.
- Сохранить `enforcement: active`, цель `~DEFAULT_BRANCH` и пустой `bypass_actors`.
- Сохранить требование PR и одного одобрения, сброс устаревших одобрений, разрешённое squash-слияние и разрешение обсуждений перед слиянием.
- Сохранить запрет force push (`non_fast_forward`).
- Добавить запрет удаления (`deletion`).
- Добавить обязательные проверки с точными именами: `Стиль кода`, `Тесты`, `Сборка образов`, `Поиск паролей`, `Публикация образа`.

Выбор исполнителя: принимать результаты проверок от GitHub Actions (`integration_id: 15368`); не вводить дополнительное требование обновлять ветку перед каждым слиянием. `Публикация образа` запускается только в main, поэтому в PR ожидается штатный статус skipped.

## Практическая проверка

1. Повторно прочитать сохранённый ruleset и сопоставить настройки с проектом.
2. В отдельном checkout от актуальной удалённой main создать небольшой проверочный коммит README и выполнить настоящий push в main. Сохранить отказ сервера и убедиться, что SHA main не изменился.
3. Открыть PR с заведомой ошибкой форматирования Python. Дождаться падения `Стиль кода` и зафиксировать блокировку слияния.
4. Убрать проверочную ошибку, дождаться успешных обязательных проверок (публикация штатно пропущена) и зафиксировать блокировку слияния из-за отсутствия одобрения.
5. Оставить в PR документацию по защите и фактические результаты проверок, указать `Closes #7`. PR готов к чтению и одобрению напарником; окончательное слияние выполняет напарник по правилам проекта.

## Границы и ограничения

Текущий checkout содержит незакоммиченные изменения сервиса заказов; проверочные коммиты выполняются отдельно. Изменения CI по карточке 1.6 и остальных ruleset в эту работу не входят. Нельзя ослаблять защиту ради проверки, добавлять исключения обхода, выдавать собственное одобрение за одобрение напарника или записывать ожидаемые отказы как уже полученные.

Исполнитель выбирает безопасное место для отдельного checkout, минимальный пример ошибки форматирования и формат отчёта. Неожиданные отказы CI отражаются по фактическим результатам.
